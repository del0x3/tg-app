# Code Review: Логические ошибки и архитектурные проблемы

## КРИТИЧЕСКАЯ ПРОБЛЕМА: Утечка конфигурации БД

**Файл:** `backend/src/shared/database.config.ts:9`

В конфигурации базы данных находится подозрительный `fetch`-вызов, отправляющий конфигурацию БД (host, port, database, NODE_ENV) на локальный endpoint `http://127.0.0.1:7243`. Даже если это "debug" код — он не должен находиться в production-конфигурации. Он помечен как `// #region agent log`, но отправляет чувствительные данные.

```typescript
// Строка 9 — УДАЛИТЬ
fetch('http://127.0.0.1:7243/ingest/...', { body: JSON.stringify({ host, port, database, ... }) })
```

## 1. Архитектурные проблемы

### 1.1. `getMasterId()` недетерминирован при нескольких мастерах

**Файлы:** `crm.service.ts:42-47`, `appointments.service.ts:28-32`, `giveaways.service.ts:41-46`

Когда обычный клиент вызывает `getMasterId()`, метод возвращает ПЕРВОГО мастера из БД (`findOne({ where: { isMaster: true } })`). При нескольких мастерах результат зависит от порядка в БД — клиент может «попасть» к случайному мастеру. Этот же метод дублируется в 3 сервисах.

**Последствие:** При добавлении второго мастера все клиентские API (booking, discount slots, giveaways) могут начать возвращать данные не того мастера.

### 1.2. Отсутствие route guard на фронтенде

**Файл:** `frontend/src/router/index.js`

Маршруты имеют `meta: { requiresMaster: true }`, но **нет `beforeEach` guard'а**, который это проверяет. Любой авторизованный пользователь может зайти на `/admin/*` страницы. API защищены через `MasterOrAdminGuard`, но UI полностью открыт — клиент видит интерфейс администратора (хоть и без данных).

### 1.3. In-memory session state (не переживает рестарт)

**Файл:** `bot.service.ts:36`

`feedbackSessions` и `quickTestSessions` хранятся в `Map` в памяти процесса. При перезапуске сервера все активные сессии фидбека и тестов теряются — пользователи «зависают» посередине процесса. При масштабировании на несколько инстансов — сессии не расшариваются между ними.

### 1.4. N+1 проблема с запросами в `getAvailableSlotsInRange()`

**Файл:** `appointments.service.ts:312-342`

Для каждого дня диапазона вызывается `getAvailableSlotsForDate()`, который делает 2 запроса к БД (слоты + бронирования). Диапазон в 30 дней = 60 запросов к БД. Нужен один запрос с группировкой по дате.

### 1.5. `sanitizeUser()` ничего не делает

**Файл:** `auth.service.ts:166-169`

```typescript
private sanitizeUser(user: User) {
  const { ...rest } = user; // <- просто копирует весь объект
  return rest;
}
```

Метод подразумевает фильтрацию чувствительных полей, но возвращает все поля без изменений.

## 2. Логические ошибки

### 2.1. Race condition: возможно двойное бронирование

**Файл:** `appointments.service.ts:344-416`

Метод `book()` проверяет доступность слота, затем создаёт запись. Между проверкой и `save()` нет блокировки — два одновременных запроса могут забронировать одно и то же время. Нужен `SELECT ... FOR UPDATE` или уникальный constraint в БД.

### 2.2. Напоминания спамят клиента если мастер заблокировал бота

**Файл:** `reminders.service.ts:119-123`

```typescript
if (clientReminderOk && masterReminderOk) {
  a.reminderSentAt = new Date();
}
```

Если сообщение клиенту отправлено, но мастеру — нет (мастер заблокировал бота), `reminderSentAt` НЕ устанавливается. На следующем цикле (через 15 мин) клиент получит то же напоминание повторно. Это будет продолжаться бесконечно.

### 2.3. Двойная отправка pre-session напоминания

**Файл:** `reminders.service.ts:52-125, 128-172`

Метод `sendDueReminders` содержит встроенную логику pre-session напоминания (строки 90-109) внутри 24h напоминания. Отдельно работает `sendPreSessionReminders()`. Если запись в пределах 10 минут И ещё не было 24h напоминания, первый метод отправляет и 24h напоминание, и drink-напоминание в одном проходе. Флаг `preSessionReminderSentAt` защищает от повтора, но логика запутанная и хрупкая.

### 2.4. Re-engagement напоминания игнорируют будущие записи

**Файл:** `client-reminders.service.ts:63-123`

Автоматические напоминания «прошло 2 недели» проверяют дату последнего DONE-визита, но НЕ проверяют, есть ли у клиента уже SCHEDULED-запись. Клиент, который уже записан на следующую неделю, всё равно получит «пора записаться».

### 2.5. `modelBooked` проверка всегда false

**Файл:** `appointments.service.ts:193`

```typescript
const modelBooked = booked.some((a) => a.slotId === slot.id && !a.serviceId);
```

Условие проверяет `!a.serviceId`, но при бронировании "для моделей" (`book()`, строка 374) `serviceId` берётся из слота и устанавливается. Эта проверка никогда не сработает для корректно созданных бронирований.

### 2.6. `updateClient` для user-only: двойная запись

**Файл:** `crm.service.ts:316-333`

При обновлении "user-only" клиента код сначала создаёт и сохраняет клиента (`clientRepo.save`), затем тут же вызывает `clientRepo.update` с теми же данными. Это лишний запрос к БД. Более того, если DTO содержит только `notes`, при создании `name` берётся из пользователя, а затем `update` может перезаписать его на `undefined`.

## 3. Проблемы безопасности

### 3.1. JWT токены без срока действия

**Файл:** `auth.service.ts:53-58`

JWT подписывается без `expiresIn`. Стратегия имеет `ignoreExpiration: false`, но если в payload нет `exp`, токен валиден вечно. Украденный токен даёт бессрочный доступ.

### 3.2. Дефолтный JWT secret

**Файл:** `auth/strategies/telegram.strategy.ts:25`

```typescript
secretOrKey: configService.get<string>('JWT_SECRET', 'your-secret-key')
```

Если `JWT_SECRET` не задан в env, используется `'your-secret-key'`. В production любой может подделать JWT-токен.

### 3.3. `synchronize: true` в не-production окружениях

**Файл:** `shared/database.config.ts:7`

```typescript
const synchronize = process.env.NODE_ENV !== 'production';
```

TypeORM `synchronize: true` может удалить данные при изменении entity. Это опасно даже в staging если там реальные данные.

## 4. Утечки данных в мультимастерской конфигурации

### 4.1. Все зарегистрированные пользователи видны всем мастерам

**Файл:** `crm.service.ts:130-136`

`registeredOnly` загружает ВСЕХ пользователей (`isMaster: false, isAdmin: false`) без фильтрации по masterId. В мультимастерской системе Мастер A видит клиентов, которые взаимодействовали только с Мастером B.

### 4.2. Дискаунт уведомления идут всем юзерам системы

**Файл:** `crm.service.ts:91-97`

```typescript
const registered = await this.userRepo.find({
  where: { isMaster: false, isAdmin: false },
});
```

При создании скидочного слота уведомление отправляется ВСЕМ зарегистрированным пользователям в системе, а не только клиентам данного мастера.

### 4.3. `getDiscountSlots()` привязан к одному мастеру

**Файл:** `appointments.service.ts:291`

`getDiscountSlots` использует `getMasterId()` (первый попавшийся мастер). В мульти-мастерской системе клиент увидит скидки только одного произвольного мастера.

## 5. Прочие проблемы

### 5.1. Giveaway draw использует `Math.random()` + sort

**Файл:** `giveaways.service.ts:237`

```typescript
const shuffled = [...participants].sort(() => Math.random() - 0.5);
```

Для розыгрыша это: (а) нечестный алгоритм — sort-based shuffle даёт неравномерное распределение; (б) `Math.random()` не является криптографически безопасным. Следует использовать Fisher-Yates + `crypto.randomInt`.

### 5.2. Временные зоны не учитываются

**Файл:** `reminders.service.ts:45-49`

`new Date('2024-01-15T10:00:00')` парсится в локальном времени сервера. Если сервер в UTC, а бизнес в UTC+3 — все напоминания отправляются на 3 часа раньше.

### 5.3. Broadcast без rate limiting

**Файл:** `auth.service.ts:143-160`

`broadcastMessage` отправляет сообщения всем пользователям в цикле без задержек. Telegram Bot API имеет лимит ~30 сообщений/сек. При большом количестве пользователей бот будет заблокирован за спам.

### 5.4. `escapeHtml()` дублируется 4 раза

**Файлы:** `crm.service.ts:671`, `bot.service.ts:46`, `appointments.service.ts:470`, `reminders.service.ts:175`

Одна и та же функция `escapeHtml` написана 4 раза в разных файлах, причём с разными реализациями (одна экранирует `"`, другие — нет).
